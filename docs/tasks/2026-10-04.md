    schemas on every request today.

    name (`x5_get_status`) resolves to `device_x5_get_status` in tool_search,
    tool_call and the unknown-name repair; tool_search says a device tool is

- [ ] **2. Web chat: a message shows as sent AND queued, then sends again (loops).**
  Screenshot: the message bubble + "Thinking", and the same text in the queue
  chip; after the reply, the same question is sent again.
  - Found (server log 18:02:22): `POST /api/chat/start?stream=1` → 200 (the
    turn started), then a plain `POST /api/chat/start` → **409** "session
    already has an active stream" → the web UI queued the message → re-sent it
    at 18:04:32 after the reply.
  - Root cause: the server opens the stream with an event named `chat_start`;
    the web client only accepts `start` (both from 5cca1b3a54, 2026-09-04). So
    the first message after every page load counted as "server doesn't stream",
    was posted a second time, 409'd and was queued. The iPhone app gets this
    right (a 2xx start is committed, never re-posted).
  - ✅ Fixed (d2259befe5): the client accepts `chat_start`; a 2xx stream is never
    posted again (reattach instead); a 409 queues once; a still-queued message
    is no longer copied into the composer too. Contract tests run the client's
    own function in node on the server's real first frame (fail on old code).
